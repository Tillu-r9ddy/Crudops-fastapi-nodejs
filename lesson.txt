The Big Picture First
Before any code, understand what you built:


Browser (React)
    ↕  HTTP requests
FastAPI (Python, port 8000)  ←→  tasks.db (SQLite file on disk)
Node.js (Express, port 3001) ←→  tasks.db (SAME file)
React is the face. FastAPI and Node.js are two backends doing the exact same job differently, sharing one database. The database is a single file called tasks.db. This architecture lets you compare how Python and JavaScript solve identical problems.

Part 1 — The Database Layer (SQLite)
Before explaining the backends, you need to understand what SQLite is, because both backends talk to it.

SQLite is a database that lives in a single file (tasks.db) on your hard drive. No separate server needed — the file IS the database. Perfect for learning.

The tasks table looks like this:


| id | title       | description  | completed | created_at          |
|----|-------------|--------------|-----------|---------------------|
|  1 | Buy milk    | from store   | 0         | 2026-05-11T08:00:00 |
|  2 | Learn React |              | 1         | 2026-05-11T09:00:00 |
That's it. Five columns. Everything you build revolves around reading and writing this table.

__file__ is Python's built-in variable that holds the path to the current file. So __file__ = ...CRUDOPS/backend/main.py.
.parent goes one folder up → ...CRUDOPS/backend/
.parent again → ...CRUDOPS/
/ "tasks.db" adds the filename → ...CRUDOPS/tasks.db
The URL format sqlite:/// is how SQLAlchemy identifies SQLite. Three slashes + absolute path.
Why not just write the path directly? Because the path depends on where the project lives on your machine. Using __file__ makes it work on any machine automatically.


engine = create_engine(DATABASE_URL, connect_args={"check_same_thread": False})
create_engine sets up the database connection pool. Think of it as the "bridge" between Python and the file.
check_same_thread=False — SQLite by default only allows one thread to use the same connection. FastAPI uses multiple threads, so we disable this restriction.

@event.listens_for(engine, "connect")
def set_wal_mode(dbapi_conn, _):
    cursor = dbapi_conn.cursor()
    cursor.execute("PRAGMA journal_mode=WAL")
    cursor.close()
@event.listens_for(engine, "connect") — This is a decorator. Every time a new connection to the database is opened, this function automatically runs.
PRAGMA journal_mode=WAL — WAL = Write-Ahead Log. A SQLite setting that allows one process to write while another is reading at the same time. Without this, FastAPI and Node.js would fight over the database file and one would get a "database is locked" error.

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
sessionmaker creates a factory. Every time you call SessionLocal(), you get a fresh database session.
autocommit=False — Changes are NOT saved automatically. You must call db.commit() explicitly. This gives you control over transactions.
autoflush=False — SQLAlchemy won't automatically write pending changes before queries.

class Base(DeclarativeBase):
    pass
Base is the parent class all your database models inherit from. SQLAlchemy uses it to track all your tables.
The ORM Model (lines 37–47)

class TaskModel(Base):
    __tablename__ = "tasks"

    id          = Column(Integer, primary_key=True, index=True)
    title       = Column(String, nullable=False)
    description = Column(String, default="")
    completed   = Column(Boolean, default=False)
    created_at  = Column(DateTime, default=lambda: datetime.now(timezone.utc))
This Python class maps directly to the tasks table in SQLite. Each attribute = one column.

__tablename__ = "tasks" — Tells SQLAlchemy the actual SQL table name.
Column(Integer, primary_key=True, index=True) — id is an auto-incrementing integer. primary_key=True means SQLite will assign 1, 2, 3... automatically. index=True makes lookups by id faster.
Column(String, nullable=False) — title must always have a value. Cannot be NULL.
default="" — If description isn't provided, store empty string.
default=lambda: datetime.now(timezone.utc) — A lambda (anonymous function). Called each time a row is created to get the current UTC time. We use a lambda (not just datetime.now(timezone.utc)) because otherwise Python would calculate the time once when the file loads, not at insert time.

Base.metadata.create_all(bind=engine)
This is very important. When FastAPI starts, this line looks at all your models (TaskModel), checks if the tasks table exists, and creates it if it doesn't. It's like running CREATE TABLE IF NOT EXISTS automatically.

Pydantic Schemas (lines 53–76)
Here's the key concept: ORM models are for talking to the database. Pydantic models are for talking to the outside world (HTTP requests/responses). They're different things.


class TaskCreate(BaseModel):
    title: str
    description: str = ""
When someone sends a POST request to create a task, the JSON body must look like {"title": "buy milk"}. Pydantic parses it into a TaskCreate object. description is optional (defaults to "").


class TaskUpdate(BaseModel):
    title:       Optional[str]  = None
    description: Optional[str]  = None
    completed:   Optional[bool] = None
For updating, ALL fields are optional (you might only want to toggle completed without changing the title). Optional[str] = None means: this field might not be sent at all.


class TaskOut(BaseModel):
    id:          int
    title:       str
    description: str = ""
    completed:   bool = False
    created_at:  Optional[datetime] = None

    @field_validator("completed", mode="before")
    @classmethod
    def coerce_completed(cls, v):
        return bool(v) if v is not None else False

    model_config = {"from_attributes": True}
TaskOut is what FastAPI sends back to the browser in the response.

@field_validator("completed", mode="before") — Before Pydantic validates the completed field, run this function. mode="before" means it runs on the raw incoming value.
coerce_completed — SQLite stores booleans as integers (0 or 1). This validator converts 0 → False, 1 → True, None → False. Without this, Pydantic would reject SQLite's integers.
model_config = {"from_attributes": True} — Allows Pydantic to read from SQLAlchemy model instances (which have attribute access like task.title) instead of requiring a plain dictionary.

allow_origins=["*"] — Allow requests from ANY domain. In production you'd put ["https://yoursite.com"] here.

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
This is a generator function (notice yield not return). It's FastAPI's dependency injection pattern for database sessions.

Opens a new session with SessionLocal()
yield db — passes the session to the route handler that needs it, pauses here
After the route finishes (success OR error), Python resumes after yield and runs db.close() in the finally block
The finally guarantees the session is ALWAYS closed, even if an exception happened

POST /tasks — Create


@app.post("/tasks", response_model=TaskOut, status_code=201)
def create_task(body: TaskCreate, db: Session = Depends(get_db)):
    task = TaskModel(**body.model_dump())
    db.add(task)
    db.commit()
    db.refresh(task)
    return task
body: TaskCreate — FastAPI reads the JSON request body and validates it into a TaskCreate object automatically.
status_code=201 — HTTP 201 means "Created". More semantically correct than 200 for a new resource.
body.model_dump() — Converts the Pydantic model to a plain Python dictionary: {"title": "buy milk", "description": ""}.
TaskModel(**body.model_dump()) — ** unpacks the dict into keyword arguments. Same as TaskModel(title="buy milk", description="").
db.add(task) — Tells SQLAlchemy "remember this new row".
db.commit() — Actually writes it to the database file.
db.refresh(task) — After commit, the database fills in auto-generated values (like id and created_at). refresh re-reads the row so the Python object has these values.
PUT /tasks/{task_id} — Update


@app.put("/tasks/{task_id}", response_model=TaskOut)
def update_task(task_id: int, body: TaskUpdate, db: Session = Depends(get_db)):
    task = db.query(TaskModel).filter(TaskModel.id == task_id).first()
    if not task:
        raise HTTPException(status_code=404, detail="Task not found")
    for field, value in body.model_dump(exclude_none=True).items():
        setattr(task, field, value)
    db.commit()
    db.refresh(task)
    return task
body.model_dump(exclude_none=True) — Converts to dict but skips fields that are None. If the frontend only sends {"completed": true}, the dict is just {"completed": True} — title and description are excluded, so they won't be overwritten.
for field, value in ...items() — Loops over each sent field.
setattr(task, field, value) — Dynamically sets the attribute. Same as task.completed = True but works for any field name.
DELETE /tasks/{task_id} — Delete


@app.delete("/tasks/{task_id}", status_code=204)
def delete_task(task_id: int, db: Session = Depends(get_db)):
    task = db.query(TaskModel).filter(TaskModel.id == task_id).first()
    if not task:
        raise HTTPException(status_code=404, detail="Task not found")
    db.delete(task)
    db.commit()
status_code=204 — HTTP 204 means "No Content". Deletion succeeded, nothing to send back. That's why there's no return statement.
db.delete(task) — Marks the object for deletion.
db.commit() — Executes the DELETE SQL.

POST /tasks — Create


app.post("/tasks", (req, res) => {
  const { title, description = "" } = req.body
  if (!title || !title.trim()) {
    return res.status(400).json({ error: "title is required" })
  }
  const result = db
    .prepare("INSERT INTO tasks (title, description) VALUES (?, ?)")
    .run(title.trim(), description.trim())
  const task = db.prepare("SELECT * FROM tasks WHERE id = ?").get(result.lastInsertRowid)
  res.status(201).json(normalise(task))
})
const { title, description = "" } = req.body — Destructuring. Extracts title and description from the request body. If description is missing, defaults to "".
? in the SQL — Parameterized query. SQLite replaces ? with the actual values safely. Never concatenate user input directly into SQL — that's SQL injection.
.run(...) — Executes an INSERT/UPDATE/DELETE (not a SELECT).
result.lastInsertRowid — The auto-generated id of the just-inserted row.
PUT /tasks/:id — Update


const title       = req.body.title       ?? task.title
const description = req.body.description ?? task.description
const completed   = req.body.completed   !== undefined
    ? (req.body.completed ? 1 : 0)
    : task.completed
?? is the nullish coalescing operator. a ?? b means: use a if it's not null/undefined, otherwise use b. This lets partial updates work — if you don't send title, it keeps the existing one.

Part 5 — Frontend: API Layer (src/api.ts)
This file is a clean abstraction — it hides all the raw fetch details from the rest of your app.


const BASE: Record<Backend, string> = {
  fastapi: "http://127.0.0.1:8000",
  nodejs: "http://127.0.0.1:3001",
}
Record<Backend, string> — A TypeScript type that says "an object where every key is a Backend and every value is a string". TypeScript will error if you forget one of the backends.


async function request<T>(backend: Backend, path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE[backend]}${path}`, {
    headers: { "Content-Type": "application/json" },
    ...init,
  })
  if (res.status === 204) return undefined as T
  const data = await res.json()
  if (!res.ok) throw new Error(data.detail ?? data.error ?? `HTTP ${res.status}`)
  return data
}
<T> — A generic. T is a placeholder type. When you call request<Task[]>(...), TypeScript knows the return type is Task[]. This gives you type safety throughout.
init?: RequestInit — The ? means optional. RequestInit is the browser's built-in type for fetch options (method, body, headers, etc.).
...init — Spread operator. Merges init's properties into the options object. If init has method: "POST", it gets added.
if (res.status === 204) return undefined as T — DELETE returns 204 No Content (no JSON body). We return undefined and tell TypeScript "trust me, this is the right type".
data.detail ?? data.error — FastAPI uses detail for errors. Node.js uses error. The ?? tries detail first, falls back to error.

export const api = {
  getTasks:   (b) => request<Task[]>(b, "/tasks"),
  createTask: (b, payload) => request<Task>(b, "/tasks", { method: "POST", body: JSON.stringify(payload) }),
  updateTask: (b, id, payload) => request<Task>(b, `/tasks/${id}`, { method: "PUT", body: JSON.stringify(payload) }),
  deleteTask: (b, id) => request<void>(b, `/tasks/${id}`, { method: "DELETE" }),
}
These four functions are the only thing the rest of the app uses to talk to the backend. Clean, named, typed.

useEffect(() => { fetchTasks() }, [fetchTasks]) — Runs fetchTasks whenever fetchTasks changes. Since fetchTasks only changes when backend changes, this effectively means: fetch tasks whenever the active backend switches. This is how the page reloads data when you click the FastAPI/Node.js toggle.

Mutations (lines 38–72)
Each handler calls the API, then updates local state without re-fetching from the server:


async function handleCreate(title: string, description: string) {
  const task = await api.createTask(backend, { title, description })
  setTasks(prev => [task, ...prev])  // add new task to FRONT of list
}

async function handleToggle(id: number, completed: boolean) {
  const updated = await api.updateTask(backend, id, { completed })
  setTasks(prev => prev.map(t => t.id === id ? updated : t))
  // replace the one task, keep everything else
}

async function handleDelete(id: number) {
  await api.deleteTask(backend, id)
  setTasks(prev => prev.filter(t => t.id !== id))
  // remove the deleted task from the list
}
prev => prev.filter(...) — This pattern using prev (the previous state) is important. React state updates can be asynchronous, so always use the function form when new state depends on old state.

Early return pattern — if editing is true, render a completely different UI and return early. Otherwise fall through to the normal view.


const formattedDate = task.created_at
  ? new Date(task.created_at.endsWith("Z") ? task.created_at : task.created_at + "Z").toLocaleString()
  : ""
endsWith("Z") — Z at the end of a date string means UTC timezone. FastAPI returns dates without Z. Without appending Z, new Date() treats it as local time, which would show the wrong time.
.toLocaleString() — Formats the date according to the user's local settings.

<input
  type="checkbox"
  checked={task.completed}
  onChange={() => onToggle(task.id, !task.completed)}
  style={{ ..., accentColor } as React.CSSProperties}
/>
checked={task.completed} — The checkbox is controlled by React. Checked = true, unchecked = false.
onChange={() => onToggle(task.id, !task.completed)} — When clicked, calls the parent's toggle function with the OPPOSITE of the current completed value.
accentColor in the style — CSS accent-color property changes the checkbox's tick color to match the active backend's color.
The Complete Flow — How Everything Connects
Here's what happens when you type a task title and click "Add Task":


1. TaskForm: user types in <input>
      → onChange fires → setTitle("buy milk") → React re-renders

2. TaskForm: user clicks "Add Task"
      → handleSubmit fires → e.preventDefault()
      → calls onSubmit("buy milk", "") which is App.handleCreate

3. App.handleCreate:
      → calls api.createTask("fastapi", { title: "buy milk", description: "" })

4. api.ts request():
      → fetch("http://127.0.0.1:8000/tasks", { method: "POST", body: '{"title":"buy milk","description":""}' })

5. FastAPI receives POST /tasks:
      → Pydantic validates body → creates TaskCreate { title: "buy milk", description: "" }
      → get_db() opens a Session
      → TaskModel(title="buy milk", description="") created
      → db.add() + db.commit() → SQL: INSERT INTO tasks (title, description) VALUES (...)
      → db.refresh() → row now has id=2, created_at=2026-05-11T...
      → Returns TaskOut as JSON: { "id": 2, "title": "buy milk", ... }

6. api.ts: fetch resolves → data parsed → returned as Task object

7. App.handleCreate:
      → setTasks(prev => [newTask, ...prev])
      → React re-renders with the new task at the top of the list

8. TaskList re-renders → TaskItem rendered for the new task → user sees it
